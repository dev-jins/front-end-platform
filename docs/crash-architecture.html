Crash Games Architecture

Crash is a second game family that lives next to slots, not instead of them. Like slots, crash games speak our canonical protocol through a transport port (gateway · direct · mock), so one crash client can run on several providers. What is new: a live event stream that the gateway relays from each provider's realtime channel. Provider A's native API is docs/crash-api.md (Game API + Mercure). Companion to the client architecture and the multi-provider gateway.

1. Recommendation in one view

"Sockets" here means a server push stream

Provider A pushes over Mercure (SSE). Other providers may use WebSocket or polling. The client never sees which: it receives our canonical event stream from the gateway (SSE), and sends commands over HTTPS /v1/play, exactly like slots.

protocol One port, three transports

CrashTransport: init, play, subscribe. Gateway in production, Direct for Provider A before the gateway exists, Mock for dev and tests.

gateway Relays the stream

Connectors subscribe upstream (Mercure / WS / poll), translate with the provider's pure mapper, fan out public round events once per room, and add seq + serverTime.

mappers Per provider, pure

mappers/provider-a/crash turns native events, snapshots and commands into canonical ones. Same file runs in the browser (Direct) and in the gateway connector.

game-core Event reducer

No nextStep loop. Stream starts with a snapshot, then ordered events fold into the store. React and Pixi only read the store.

Not recommended

Client code that knows Mercure topics, subscriberToken or bet_ok outside the provider mapper · one upstream connection per player for public round data · a client build per provider · native EventSource (no auth header).

2. Slots and crash side by side

The platform hosts game families. Each game app picks one family; the lobby, launch, gateway and session handling are shared. Nothing in the slot path changes to add crash.

Family folders, not forks

A crash/ folder next to slot/ in protocol, game-core, renderer, hud and each provider mapper — the "group by game family" rule already in the repo.

A game is one family

Catalog and init carry family: "slot" | "crash". A game app imports only its family's code, so bundles stay small.

Shared parts move to common

Balance, errors, session, i18n, popups, sound, asset loading. Move a slot helper up only when crash actually needs it.

Gateway is one service

Same /v1/sessions, /v1/play, /v1/launch, catalog. Crash adds one endpoint: the event stream.

4. Where the gateway fits

Same three modes as in the gateway doc. The crash client depends only on CrashTransport; which transport is created comes from launch config.

Room hub (new in the gateway)

Round events are the same for every player of a game. The connector subscribes to the provider's public channel once per room (provider × game × table) and the hub fans out to all clients — not one upstream connection per player. Player-only events (own bet confirmed / settled) come from a per-session upstream and go only to that client.

Ordered, resumable stream

The hub stamps every canonical event with a per-room seq and serverTime, keeps a short replay buffer, and caches the latest room snapshot. A client reconnecting with Last-Event-ID gets the missed events, or a fresh snapshot if the gap is too old.

Secrets stay server-side

In gateway mode the fingerprint, subscriberToken and Mercure topics live in the connector's session map. The client only has our gateway token — the 112 self-lockout can't come from the browser anymore.

What the gateway must not do

Decide crash points, cash-out multipliers or auto cash-out. It forwards commands immediately (no queueing) and passes the provider's values through. RNG and math stay at the provider.

Who decides SSE or WebSocket? Config at three levels

There are two separate links, and each one is decided in a different place. The game code never reads "SSE" or "WebSocket" itself.

Gateway mode

Client always uses SSE to our gateway (level 2). Whether the provider behind it speaks Mercure, WebSocket or polling is level 3, so adding a WebSocket provider changes only gateway config and a connector, not the game.

Direct mode

Level 1 names the provider, which picks that provider's DirectTransport from its mapper package. The provider's own init tells it the details (for Provider A: server.url, topics, subscriberToken). Only browser-safe providers are allowed here.

Why SSE to the gateway, not WebSocket

Commands already go over HTTPS /v1/play (idempotency, same as slots), so the client only needs server → client push. SSE is plain HTTP: easier through proxies and CDNs, built-in resume with Last-Event-ID. Switch to kind:"ws" only if we ever need client → server messages on the stream.

5. Canonical crash protocol

An extension of the canonical protocol: same init and /v1/play, new crash actions, a crash capabilities block, and an event stream. Designed as a superset of Provider A, as for slots.

Init POST /v1/sessions (crash part)

{
  game: { id, provider, family: "crash", clientId },
  money: { balance:"103.00", currency, decimals },
  bets: { min, max, default },
  capabilities: { crash: {
    lanes: 1 | 3,
    autoCashout: { min:"1.01" } | null,
    curve: { kind:"exp", k } | { kind:"ticks" },
    liveBets: true,
    betWhileRunning: "reject" | "nextRound",
    freeRounds: false
  }},
  stream: { kind:"sse", url:"/v1/stream" },
  promos, i18n
}

Commands POST /v1/play

// request
{ requestId:"uuid", action:"bet",
  lane:1, bet:"1.00", autoCashout:"2.00" }
// action: bet | cancelBet | cashout
// lane always sent; connector drops it
// for providers without lanes

// response
{ balance:"102.00",
  bet?: { roundId, lane, amount, autoCashout },
  cashout?: { multiplier:"1.84", win:"1.84" } }

Stream GET /v1/stream (SSE)

// every event
{ seq:1042, serverTime:1764090000123,
  type:"tick", lane:1, roundId:"r-88",
  multiplier:"1.37" }

// first event on every connect
{ seq:1000, type:"snapshot",
  lanes:[…], history:[…], topWins:[…],
  myBets:[…], balance:"102.00" }

Batching for scale

The hub may coalesce live-bet events into one betsDelta every ~200 ms per room. Tick and phase events are never batched.

Unknown events

Client logs and skips unknown types, as the slot event player does. Provider-specific extras travel in ext.

Errors

Canonical taxonomy from the gateway doc, plus crash codes: BETTING_CLOSED, ROUND_CRASHED (cash-out too late), NO_ACTIVE_BET, ALREADY_CASHED_OUT. Connector maps native codes.

6. Same game, different providers

As with Fruit Storm: one client build (clientId), several catalog entries. The provider supplies the round, the math and the money; we supply the client.

Catalog

[
  { id:"prov-a:rocket", provider:"prov-a",
    family:"crash", clientId:"crash-rocket" },
  { id:"prov-b:rocket-x", provider:"prov-b",
    family:"crash", clientId:"crash-rocket" }
]

Launch returns the same game URL; the gateway token says which provider and room is behind it.

What each mapper absorbs

  • Realtime channel: Mercure / WebSocket / polling
  • Auth: subscriber tokens, HMAC, fingerprints
  • Event names and shapes → canonical events
  • Money: decimal strings vs integer cents
  • Lanes: keyed objects, arrays, or none
  • Cash-out style: "cash out now" vs "cash out at m"
  • Native error codes → canonical errors

What capabilities express

  • lanes 1 or 3 → HUD shows 1 or 3 bet slots
  • autoCashout missing → hide the field
  • curve formula or ticks-only
  • liveBets: false → hide the live list
  • betWhileRunning → "next round" button or disabled

When it is NOT the same game

Same client only if the mechanic matches: one rising multiplier per lane, bet in countdown, cash out while running. A provider with different rules (multi-step cash-out, betting on ranges, different visual concept) gets its own clientId, even with a similar name. Also confirm certification allows our client on that provider's math in each market.

7. Client runtime layers

React and Pixi never touch the network. game-core holds one CrashTransport and never knows the mode or the provider.

8. Connect & resync

game-core sees the same thing in every mode: a stream whose first event is snapshot, followed by ordered events. Who builds that guarantee depends on the transport.

Gateway mode

  • POST /v1/sessions → token, capabilities
  • Open /v1/stream with Authorization (fetch-based SSE reader)
  • Hub sends snapshot then live events with seq
  • Reconnect with Last-Event-ID; hub replays or re-snapshots

Direct mode (prov A, phase 0)

  • GET /game/{sessionKey} once (fingerprint rotates)
  • Open Mercure with both topics on one connection, buffer events
  • GET /crash/myStats → mapper → synthetic snapshot
  • Replay buffer, dropping events older than the snapshot
  • On reconnect: repeat the last three steps — never re-init (112)

Mock mode

  • Recorded timeline from the gateway audit log
  • Fake clock; tests drive countdown → crash in milliseconds

Why not native EventSource

Both our gateway stream and Mercure want an Authorization header, which EventSource can't send. Use fetch + ReadableStream with a small SSE parser, or @microsoft/fetch-event-source.

Background tabs

On visibilitychange → visible, reconnect and take the fresh snapshot instead of trusting stale state. Pause the Pixi ticker while hidden.

Connection status

connecting · live · reconnecting · offline in the store. Bet and Cash out are disabled unless live; a drop mid-round shows a banner, never a guessed result.

9. Round lifecycle (per lane)

A pure reducer in game-core: (state, canonicalEvent) → state. Provider phase names never reach it.

10. Store shape

type LaneId = 1 | 2 | 3;

interface CrashState {
  connection: "connecting" | "live" | "reconnecting" | "offline";
  capabilities: CrashCapabilities;
  lanes: Record<LaneId, LaneState>;  // lanes: 1 → only lane 1
  history: RoundResult[];
  topWins: Bet[];
  myBets: MyBetRecord[];
  balance: string;
  lastSeq: number;
  clockOffsetMs: number;              // from serverTime
}

interface LaneState {
  roundId: string;
  phase: "starting" | "countdown" | "running" | "crashed";
  startAt: number | null;
  serverMultiplier: string;           // last tick
  crashPoint: string | null;
  myBet: MyBet | null;
  pending: "bet" | "cancel" | "cashout" | null;
  bets: Bet[];
}

Rules

  • snapshot replaces the whole state; other events patch it. Same reducer in tests.
  • Ignore events with seq ≤ lastSeq (duplicates after reconnect).
  • pending blocks double clicks; cleared by the /v1/play response or its error.
  • Command responses and player events can both carry balance: last serverTime wins.
  • The Pixi ticker reads serverMultiplier via store.getState(), not a hook.
  • Live-bet events are flushed into the store once per animation frame; the list is virtualized.

11. Rendering the multiplier

Curve from capabilities

With curve.kind = "exp", compute m = ek·t each frame from now + clockOffsetMs − startAt; ticks only correct drift. Each provider's formula arrives through capabilities, so the client has none hard-coded.

Ticks only

When a provider gives no formula: render one tick behind and tween between the last two. Never extrapolate past the latest tick.

Crash wins

On crash, snap to crashPoint and play the effect at once, even mid-tween.

Clock offset

Every canonical event has serverTime, so the offset is a running estimate — no separate time endpoint. In Direct mode, use the HTTP Date header until Provider A adds a timestamp.

12. Bet, cancel, cash out

IntentCanonicalAllowed inOn successNotes

Cash outplay {action:"cashout", lane}Running, own bet activeapply cashout.multiplier, win, balanceServer multiplier is final, not the on-screen one

Cash-out latency

The gateway adds a hop (~10–30 ms in-region). For crash that hop costs the player multiplier, so the gateway runs in the provider's region, forwards cashout without queueing, and logs end-to-end latency per provider. Show the pending state on press; never show a win before the response.

Idempotency

requestId on every command. A retried cashout after a timeout must not double-settle: the gateway returns the first result for the same requestId.

Auto cash-out

Done by the provider. The client only shows the target on the curve and waits for myBetSettled. Never fire cashout locally when the curve passes the target.

13. Lanes

One model

Everything is lanes[LaneId]; capabilities.crash.lanes says how many. A provider without lanes is a 1-lane game. HUD and renderer never branch on provider.

Lane in every command

Canonical commands always carry lane. Mapper-A drops it for Provider A's non-lane games (the API says omit it there).

Rendering

Each lane is a curve/object in one Pixi scene, not separate canvases. The layout for 1 vs 3 lanes lives in the game app.

The port

interface CrashTransport {
  init(launch: LaunchParams): Promise<CrashInit>;
  play(cmd: CrashCommand): Promise<CrashCommandResult>;
  // first event is always "snapshot"
  subscribe(handlers: {
    onEvent(e: CrashEvent): void;
    onStatus(s: ConnectionStatus): void;
  }): () => void;
  tournaments(): Promise<Tournament[]>;
}

Sits beside the slot transport. Takes and returns canonical types only; game-core imports nothing provider-specific.

Workspace chores

  • Add "./crash" to @fep/protocol exports next to "./slot". Slot code stays untouched.
  • packages/mappers/* are type:protocol-level: pure, no fetch except in their transport/ (Direct only).
  • New app → nx.tags + commitlint scope. Mapper tests use the JSON in docs/crash-api.md once full payloads exist.
