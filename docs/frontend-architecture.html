Game Frontend Architecture

Proposed client architecture for the Game Front API: a React HUD over a PixiJS canvas, a framework-free game core driven by nextStep, and a separate lobby app that launches games in iframes. Companion to the API architecture page.

1. Recommendation in one view

React HUD, lobby, modals

Bet panel, balance, popups, tournaments, nickname, settings. DOM is the right tool here.

PixiJS Reels & effects

Symbols, win lines, big win, particles at 60 fps on WebGL. Not rendered through React.

game-core Plain TypeScript

Session, fingerprint, the nextStep loop, error policy, per-game adapters. Testable without a browser.

Lobby = separate app, many lobbies

One lobby codebase, deployed as several lobbies (per provider or mix) driven by profiles from our gateway. Launches games in an iframe.

Not recommended

Module Federation for games (each launch is already a fresh session + URL; iframes free GPU memory on exit) · Next.js (no SSR benefit for a static canvas bundle) · rendering reels in DOM/CSS (frame drops on low-end Android).

2. Runtime layers

Dependencies point down only. React and Pixi never call the API directly — they read from the store and send intents (spin, buy, pick bonus) to game-core.

3. Present after animate

The response arrives in ~100 ms, the reels stop in ~2 s. If the HUD binds straight to the response, the balance and win jump before the reels land. Keep server truth and displayed state apart.

nextStep is the only driver

After commit, game-core calls the endpoint named by nextStep (auto for freespin/avalanche/respin, user-gated for spin/bonus pick).

Error policy

CRITICAL → session-over screen. ALERT (3, 112) → dialog, retry allowed. WARNING (300) → silent/log.

Recovery

On reload, init's lastSpin + mode restore the screen; resume the loop from its nextStep.

4. Monorepo layout

Nx + pnpm, same tooling as FreedX MFE. Shared code is shared at build time through packages, not at runtime.

Per-game adapter contract

interface GameAdapter {
  sysname: string
  parse(raw: unknown): NormalizedState  // Zod
  createScene(ctx): Scene              // Pixi
}

Standard games reuse the default adapter. The 7 variant games (Space Infinity, Fruit Storm, Shootland, Dark Portal, TapTap, Pinball Inferno, Mystic Gates/Charmana) ship their own. Game-specific differences never leak into hud or game-core.

5. Lobby

The lobby is a separate app. Every launch returns a new gateway token + URL of our game client, mounted in an iframe (or passed to the operator wrapper via postMessage).

Separate app + iframe (recommended)Module Federation
Session modelMatches API: fresh session per launchMust tear down / re-init session in-page
GPU memoryFreed when iframe is removedWebGL textures can leak across games
VersioningEach game ships independentlyReact / shared singletons must stay aligned

Lobby flow (through our gateway)

GET /v1/lobbies/{lobbyId} (profile) → GET /v1/lobbies/{lobbyId}/catalog (React Query, cacheable) → user picks game → POST /v1/launch {lobbyId, gameId} → mount url in iframe, or postMessage it to the operator wrapper. Card hover/press and grid transitions use Motion.

5b. Multiple lobbies, shipped per provider

Because we own the gateway, a lobby is just a profile + a deployment. One lobby codebase serves a Provider A lobby, a Provider B lobby, and a combined lobby. The gateway decides what each lobby may show and launch.

Lobby profile (stored in the gateway)

{
  "id": "lobby-b",
  "hosts": ["lobby-b.yoursite.com"],
  "providers": ["prov-b"],
  "theme": {
    "tokens": "cdn/lobbies/lobby-b/theme.json",
    "logo": "cdn/lobbies/lobby-b/logo.svg"
  },
  "layout": {
    "hero": "tournament",
    "categories": ["new", "popular", "buy-feature"]
  },
  "features": { "search": true, "tournaments": true,
                "favourites": true },
  "operators": ["op-1", "op-7"]
}

Levels of customization (use the lowest that works)

1 · Config

Providers, categories, sort order, enabled features. Pure profile data.

2 · Theme

Design tokens, logo, fonts, card style. Loaded from the profile's theme URL into CSS variables.

3 · Layout slots

Hero banner type, category rows, promo blocks — chosen by name from components in lobby-kit.

4 · Custom app

Thin apps/lobby-<id> reusing lobby-kit. Only when a lobby truly needs different code.

Rules the gateway enforces

Filter on the server

The catalog endpoint returns only the lobby's providers. Never rely on the lobby to hide games.

Guard the launch

POST /v1/launch checks gameId belongs to the lobby's providers and the operator — a hand-crafted request from Lobby B cannot start a Provider A game.

Token carries lobbyId

The game's home button returns to the lobby that launched it; analytics and tournaments can be split per lobby.

Shipping

  • Game clients — built and deployed once per game; every lobby uses the same URLs.
  • Lobby — built once, the same artifact deployed to every lobby host (or CDN path). The profile is resolved at runtime.
  • New provider lobby — add connector + profile in the gateway, point DNS. No frontend release.
  • Custom lobby (level 4) — its own CI job in the monorepo, deployed independently.

Spine vs Rive

Rive has built-in state machines but runs its own canvas runtime — awkward inside a Pixi scene. Pick Spine unless artists already work in Rive.

@pixi/react?

Fine for declaring scene structure. Per-frame reel motion stays imperative, driven from the store, so React never re-renders per frame.

Asset pipeline

TexturePacker atlases → Pixi Assets bundles per game. Send POST /stat/loaded after assets load, not on page load.
