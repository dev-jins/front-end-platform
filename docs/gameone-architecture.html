1. The full picture

Game One is a Vite + React app with two views over one store: a React HUD (balance, win, bet selector, spin button, dialogs) and a Pixi scene (reels and win lines). Neither view calls the API. The slot session in @fep/game-core/slot owns the store, sends requests through a SlotTransport, and asks the scene to present each result before committing it, so the balance and win on screen never run ahead of the reels.

ReactPixicore / contract dashed border = outside this repo
The five rules the code is built around
  1. Present after animate. A result is first pending; the scene lands the reels on it; only then do displayed and balance change. The HUD never shows a win before the reels show it.
  2. nextStep drives the game. The client never decides what comes next. Free spins, respins and cascades are played automatically because the server's nextStep says so.
  3. Init once per game start. Each GET /game/{key} rotates the fingerprint; a second tab or a second init locks the first one out (error 112). bootGame runs outside React and start() ignores repeat calls.
  4. No blind retries. A slot action has no idempotency key: after a network failure the client can't know whether the round was played, so it stops (CRITICAL) and a reload restores the truth from lastSpin.
  5. Game-specific state stays in the adapter. game-core sees a generic Round<S>; the 7 variant games will each ship their own StateAdapter.

3. Boot sequence

index.html has #game (Pixi canvas) and #root (React HUD on top). main.tsx awaits bootGame(#game) and then mounts React. start() isn't awaited, so the HUD shows "Loading…" while init is in flight.

  • The scene needs init (slot.params: reel sizes, symbols, paylines), so it's built in a one-shot store subscription once both init and displayed are set.
  • Resume before the scene exists: if the player reloads in the middle of free spins, start() will play the next free spin right after init. present awaits the sceneReady promise, so that spin waits for the scene instead of failing.
  • Layout: the scene is scaled down (never up) to fit the screen minus HUD_HEIGHT = 140 px and centred above the HUD, recalculated on renderer resize.
  • Boot failure isn't caught in main.tsx: a rejected bootGame leaves a blank page (see gaps).

6. HTTP transport & error mapping

  • createSlotHttpTransport({baseUrl, sessionKey, fetch?}) builds {baseUrl}/api/v1/game/{encodeURIComponent(sessionKey)} and sends JSON with Accept / Content-Type headers. It's stateless: the session owns the fingerprint and adds it to every body.
  • init() and tournaments() are parsed with Zod here; action() returns raw JSON, because its state part is game-specific and only the game's adapter can parse it.
  • Non-2xx responses go through toGameApiError(status, body), which picks one of the API's error channels:
HTTPBodyGameApiError.detail.kind
404anynot-found (unknown session)
422{errorCode, errorLevel, errorMessage}business — the only kind with a level
422{error}parse (body wasn't valid JSON)
400violations arrayvalidation
otheranyunexpected

Named codes: ERROR_CODE (shared: 1, 3, 4, 9, 109, 111, 112, 140, 300) and SLOT_ERROR_CODE (100–108, 110, 115: a step, bet, lines or mode the current state doesn't allow).

Round<S> = { state: S, nextStep, mode, totalWin }

Why it's shaped like this

  • displayed vs pending is present-after-animate in data form: the server's answer is visible to the renderer (pending) while the HUD still shows the previous round.
  • balance is the balance of the displayed round, not the server's latest.
  • The fingerprint is not in the store: it's a closure variable in the session, so no UI code can read or leak it.
  • Popups are sticky: a later response with null never hides a popup the player hasn't closed yet.

8. A spin, end to end

If the request fails, the phase goes from requesting straight to idle (ALERT) or over (CRITICAL), never through presenting. connectSpinView sees that and lands the spinning reels back on displayed, so the screen never shows a result that didn't happen. Starting the spin on requesting (step 4) hides the request latency: the reels move the instant the player clicks.

10. Session & intents

Every intent returns Promise<boolean>: false means "not allowed now, nothing sent"; true means it ran (including any auto steps after it). The common gate is canPlay(...steps): phase idle, no open error, a displayed round whose nextStep is one of steps.

11. State adapters

GameState isn't one schema across the catalogue: Space Infinity, Fruit Storm, Shootland, Dark Portal, TapTap, Pinball Inferno and Mystic Gates/Charmana each change it. So game-core never parses state itself. It calls adapter.parse(raw), which returns a Round<S>: the game's own state S plus the four fields the loop needs (nextStep, mode, totalWin, and the state).

  • Game One uses standardStateAdapter (gameStateSchema), so S = GameState.
  • The same adapter parses both init lastSpin and every action response; the wrapper fields (balance, popups, external free spins) are parsed separately by actionWrapperSchema.
  • A variant game would add apps/games/<sysname>/src/…-state-adapter.ts with its own schema; the HUD and scene are generic over S (the scene currently expects GameState).

13. Rendering the reels

Reel motion (pure, unit tested)

  • ReelMotion: one reel as a strip (a buffer row above + visible rows) and an offset in symbol heights. update(dtMs) accelerates to 18 symbols/s over 150 ms and scrolls; while spinning, random filler enters from the top.
  • stop(column) queues the final symbols; they scroll in, and the reel stops hard when the last one is in place. Resolves the "landed" promise.
  • ReelSetMotion: all reels, sizes from slot.params.reelsSizes. Stops are scheduled left to right: the first at max(elapsed, 500 ms), then every 150 ms.

Scene (Pixi)

  • createSlotScene: a 120×120 cell per strip row, masked to the reel window; the ticker calls motion.update then redraws positions and symbols each frame.
  • show(state): reels at rest (init lastSpin). present(state): start if needed, land on reelColumns(state.reels), draw win lines, hold 900 ms if any.
  • winLineCells maps a win line to cells: payline positions are 1-based rows; direction: "reverse" counts from the right.
  • connectSpinView drives start / fallback landing from phase changes (§8).
placeholder art Symbols are coloured rounded tiles with the symbol name (wild and scatter in yellow); no atlases, Spine, big-win timeline or landing bounce yet. Win lines are yellow frames and a polyline.

14. HUD

  • State via useSlotHudState (shallow-equal selection): phase, init, balance, and win / mode / nextStep from displayed, error, popups. The HUD re-renders on commits and phase changes, never per frame.
  • canPlay = idle ∧ no error ∧ nextStep === "spin". It gates − / +, Spin and Buy, so controls lock during auto free spins.
  • Bet: index into init.bets (bet per line); shown as total bet = bet × init.lines with exact decimal maths (multiplyMoney).
  • Win label reads "Free spins · Win" in free-spin mode; zero shows "—".
  • Buy bonus appears only with buyFeature (off for Game One): /buy on a game that doesn't sell it ends the session with 102. Price = percentOf(totalBet, bonusCoefficient).
  • Dialogs, one at a time by priority: error ("Session over" + Reload, or "Notice" + OK) → tournament start popup → tournament winner popup.
  • Money: formatMoney with currencyData.currency, rounding and the init locale; amounts never pass through floats (BigInt on scaled units + Intl string input).
  • i18n strings are inline English until packages/i18n lands.

15. Special flows

Free spins

A spin or buy returns nextStep: "freespin" and mode: "freespin". run() keeps calling /freespin — present, commit, repeat — until nextStep is back to spin. The HUD is locked the whole time because canPlay needs nextStep === "spin". An ALERT mid-chain stops it; "OK" (dismissError) resumes it.

Operator free spins handoff

When a response carries externalFreespins.nextSessionKey, the current session is closed by the server. run() creates a new transport for that key, runs init() again (new fingerprint, new lastSpin) and continues on the new session — no reload needed.

Reload mid-feature

Init returns lastSpin with its nextStep. start() calls run(null) after init, so an auto step resumes immediately; a user step (bonus, jackpot) waits for the player. The scene shows lastSpin at rest first.

Bonus & jackpot

The session supports bonus(variant), openFieldItem and next(), but no UI calls them yet: if Game One's server ever returns those steps, the HUD has no button for them and stays locked.
