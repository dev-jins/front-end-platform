Architecture

This follows docs/frontend-architecture.html. Dependencies point down only. React and Pixi never call the API: they read the game-core store and send intents. Each layer is an Nx tag, and @nx/enforce-module-boundaries fails lint on an upward import.

Every package is split by game family. Shared code sits under common/ and is exported from the package root (@fep/protocol, @fep/game-core); slot code sits under slot/ and is exported from /slot. A crash-game family, which would use sockets and a round stream, can be added as /crash without touching slots. One family never imports another.

protocol: the API contract

Zod schemas, error mapping and the HTTP transport for the Game Front API. Types come from z.infer, so the schema and the type can't drift apart.

Entry pointContents
@fep/protocolnumericStringSchema, balance, error levels and the three error-body shapes, GameApiError, toGameApiError, ERROR_CODE (1, 3, 4, 9, 109, 111, 112, 140, 300), tournaments and both popups
@fep/protocol/slotInit response, standard GameState, action wrapper, SLOT_ERROR_CODE (100–108, 110, 115), SlotTransport, createSlotHttpTransport
@fep/protocol/testingdocExamples(heading): the JSON examples parsed straight out of the API markdown

API traps the schemas handle

  • Money is a numeric string. A number is rejected, so a float never enters the client.
  • bets[] items arrive as numbers or strings, depending on the operator. They are normalised to strings.
  • extra is [] outside freespin and bonus modes, not an object, so the schema accepts either an empty tuple or the freespin object.
  • Tournament userData.place can be the string "-".
  • Init can report an error inside its HTTP 200 (codes 109, 111, 300). In that case the tournament fields are absent.
  • socials has two shapes: {nickname} or {needToRequestNickname}.

Why game state stays unparsed

Seven games (Space Infinity, Fruit Storm, Shootland, Dark Portal, TapTap, Pinball Inferno, Mystic Gates/Charmana) replace or drop standard state fields. Typing the state as one interface would be wrong for them. So init().lastSpin is unknown and action() returns raw JSON, and each game's adapter parses its own state. Standard games use standardActionResponseSchema.

Transport

  • One transport per session. It percent-encodes the session key (keys contain $ and /).
  • It is stateless: it does not hold the fingerprint, which belongs to game-core.
  • Non-2xx responses become GameApiError with detail.kind set to business (422), validation (400), parse (422 {error}), not-found (404) or unexpected.
  • The default fetch is wrapped, so the browser never calls it unbound (which throws "Illegal invocation").

Contract tests from the doc. The tests read the JSON examples straight from docs/Test Game Front API.md. If someone edits an example in a way that breaks the client, the build fails.

game-core: the slot session

createSlotSession() owns the session rules from the architecture doc. Its state lives in a zustand/vanilla store made by createSlotStore(), with no React, so the HUD and the renderer can both subscribe to it.

Session phases

Spin lifecycle: present after animate

The response arrives in about 100 ms, but the reels take seconds to land. If the HUD showed the server result directly, the balance and win would change before the reels stopped. The session keeps the server result (pending) separate from what the screen shows (displayed, balance):

Rules it enforces

  • Init exactly once. Every init rotates the fingerprint, so a second call locks out the player's own tab with error 112. start() ignores repeat calls. The fingerprint is kept inside the session, never in the store.
  • nextStep is the only driver. Freespin, respin and avalanche continue automatically, including after a reload into a freespin series. Spin, buy, bonus, open-field-item, jackpot and getPreviousState are player intents.
  • Guarded intents. An intent returns false and sends nothing when the server isn't expecting that step, or when the bet, lines, bonus variant or cell would be rejected. The API answers those mistakes with CRITICAL errors that end the session, so they are caught locally first.
  • Operator freespins handoff. When externalFreespins.nextSessionKey arrives, the session switches to a new transport and runs init on the new key.

gameone: wiring the game

  • game.ts boots once, outside React. React StrictMode runs effects twice in dev, which against the real API would mean a second init and an immediate 112 lockout.
  • The scene is built as soon as init lands. Its present() waits for a scene-ready promise. A reload into free spins resumes before start() resolves, and building the scene after start() would have deadlocked.
  • dev/mock-transport.ts serves base-game spins when VITE_API_URL and ?sessionKey= are absent. Every third spin is a scripted three-symbol win on payline 6.
  • Layout scales the reels to fit above the HUD on resize, down to phone width.

hud: the React overlay

<SlotHud session={session} buyFeature? onReload? /> reads the store through useSlotHudState and renders:

  • Balance and win; win shows "—" when zero, and the label reads "Free spins · Win" during a series.
  • A − / + bet stepper through the allowed bets, showing the total bet (bet × lines).
  • Spin, and an optional Buy bonus button priced at total bet × bonusCoefficient%. It is opt-in per game, because /buy on a game without the feature ends the session (102).
  • Error dialogs by level, and tournament start and winner popups shown one at a time.
  • Controls are enabled only when the session is idle, no dialog is open and the server expects a spin.

Money without floats

Amounts are multiplied on BigInt-scaled strings and formatted by Intl.NumberFormat using string input, rounded to currencyData.rounding. A float would get these wrong:

Running build in the same run-many as typecheck can fail gameone:typecheck with TS6305 ("output file has not been built from source"): the build writes dist/ while typecheck reads it. Run as two commands, both pass.

Browser checks (Playwright, mock backend)

  • Load restores lastSpin. During a spin the reels scroll inside the mask, the controls lock, and the balance doesn't change until the reels land.
  • At bet 25 × 10 lines the balance went $10,000 → $9,750 → $9,500, and the third spin's $125 win gave $9,375. The win line was drawn on payline 6.
  • At 375 px wide the reels scale down and the HUD wraps to two rows without horizontal scrolling.
