Multi-Provider Game Gateway

How to make one lobby and one set of generic game clients work with the current Game API and other game providers. Compares a frontend adapter layer, a server-side proxy, and a hybrid, then details the recommended design: a canonical game protocol behind a Game Gateway.

1. The problem

Today the game client speaks the Game API directly: sessionKey in the path, fingerprint in the body, nextStep drives the flow, errors are numeric codes. Another provider will differ in every one of these.

Session & auth

Path key + fingerprint here; elsewhere bearer tokens, HMAC-signed requests, operator tokens that must never reach the browser.

Flow model

nextStep here; elsewhere state enums, "feature pending" flags, or a server push over WebSocket.

Outcome shape

Reels + winLines here (plus 7 game-specific variants); elsewhere symbol IDs, cluster pays, cents as integers.

Errors

Codes 3/109/112… here; elsewhere string codes, HTTP-only errors, different severity rules.

Goal: game clients and lobby code are written once against our own structure, and each provider is a pluggable connector.

2. Three options

① Frontend adapter layer

Each provider's API is called from the browser and converted to our structure by a client-side adapter. No servers to run, but secrets, CORS and every provider change live in the game bundle.

② Server gateway

A backend-for-frontend that speaks one canonical protocol to all clients and translates to each provider server-to-server. Clients never know which provider they are on.

③ Hybrid

Client codes against a GameTransport interface. Production uses the gateway transport; a direct transport is allowed for browser-safe providers, and a mock transport for development.

Recommendation: ③ Hybrid, with the gateway as the default path

Put translation on the server (security, single place to change, idempotency, audit), but make the client depend only on a GameTransport interface. You get a mock transport for free, and you can start with a client-side adapter for the current Game API before the gateway exists — then swap the transport without touching game code.

3b. Hybrid mode explained

The core idea in one sentence

Hybrid is not a third server and not "call two backends at once". It is a code-structure rule: game code depends only on a GameTransport interface, and provider translation lives in a pure-function package that can run either in the browser or inside the gateway. Picking a mode means picking which transport is created when the game starts.

Three layers

1 · Port — GameTransport

A TypeScript interface with init(), play(), tournaments(). Takes and returns canonical types only. HUD, renderer and game-core import nothing else.

2 · Transports — how bytes travel

Gateway: canonical HTTPS to our server. Direct: provider's native API from the browser. Mock: recorded JSON, no network. Each one implements the port.

3 · Mappers — how data is translated

One package per provider: pure functions toNative(cmd) and toCanonical(raw). No fetch, no secrets, no DOM. Because they are pure, the same file runs in the browser (Direct) and on the server (gateway connector).

The code

packages/protocol — the port

export interface GameTransport {
  init(launch: LaunchParams): Promise<CanonicalInit>
  play(cmd: PlayCommand): Promise<PlayResult>
  tournaments(): Promise<Tournament[]>
}

packages/mappers/provider-a — shared, pure

// no fetch, no secrets: runs in browser AND server
export function toNative(cmd: PlayCommand) {
  const path = cmd.action === 'cascade' ? 'avalanche' : cmd.action
  return { path, body: { bet: cmd.bet, lines: cmd.params?.lines } }
}
export function toCanonical(raw: unknown): PlayResult {
  const s = GameApiState.parse(raw)        // Zod
  return { next: { action: mapStep(s.nextStep) },
           balance: s.balance.amount, events: toEvents(s), … }
}

DirectTransport (browser)

class DirectTransport implements GameTransport {
  #fingerprint = ''   // lives in the tab
  async play(cmd) {
    const { path, body } = toNative(cmd)
    const raw = await post(
      `${api}/game/${key}/${path}`,
      { ...body, fingerprint: this.#fingerprint })
    return toCanonical(raw)
  }
}

GatewayTransport (browser)

class GatewayTransport implements GameTransport {
  async play(cmd) {
    return post(`${gw}/v1/play`, {
      ...cmd, requestId: crypto.randomUUID()
    }, { token })          // already canonical
  }
}

Choosing at startup

// launch config comes from the lobby / gateway
// { transport: 'gateway', provider: 'prov-a', … }
const transport =
  cfg.transport === 'direct'  ? new DirectTransport(cfg)
: cfg.transport === 'mock'    ? new MockTransport(cfg)
:                              new GatewayTransport(cfg)

startGame(transport)   // game never asks which one

How one spin travels in each mode

Gateway mode

  • Game calls transport.play({action:'spin'})
  • Browser → gateway: canonical JSON + requestId
  • Gateway: toNative() → adds the stored fingerprint → calls provider
  • Gateway: toCanonical() → stores result → returns

Direct mode

  • Game calls transport.play({action:'spin'})
  • Browser: toNative() → adds fingerprint from the tab
  • Browser → provider native API
  • Browser: toCanonical() → returns to game

Mock mode

  • Game calls transport.play({action:'spin'})
  • Returns the next recorded canonical round (with a small delay)
  • No network, no money — for UI work and tests

When is Direct mode allowed for a provider?

  • The provider's API is meant to be called from a browser (like the current Game API: session key in URL, fingerprint returned to the client)
  • No API keys, HMAC signing or operator credentials needed per request
  • The provider allows your game domain via CORS
  • The provider can return the last round after a lost response, so the client can recover without retrying the bet
  • The market does not require you to keep your own round audit log

If any item fails, that provider is gateway-only.

How a provider moves between modes over time

B — signed RGS——Gateway only (needs secrets)
Any provider in devMock, with rounds recorded from the gateway audit log

What does NOT change when switching modes

HUD, renderer, game-core, feature modules, game tests. Moving Provider A from Direct to Gateway is a config change plus deploying the connector — the mapper code is already written and tested.

What it costs

Two transports to maintain instead of one. They are thin (~50 lines each) because all translation is in the shared mapper, which is tested once with fixtures.

Rule of thumb

Mode is chosen once per session from launch config. Never switch transport mid-round, and never call two transports for the same action.

4. Recommended architecture

The Game Gateway is an anti-corruption layer: provider concepts stop at the connectors; everything above speaks the canonical protocol. The current Game API is just "Provider A".

What the gateway does

  • Translates requests and responses
  • Maps sessions and keeps provider secrets
  • Deduplicates retries (requestId)
  • Normalizes errors and capabilities
  • Logs every round for audit and replay

What it must not do

  • Generate or alter outcomes (RNG and math stay certified at the provider)
  • Hold balances
  • Cache play results beyond the idempotency window

Connector interface

interface ProviderConnector {
  id: string
  init(launch): Promise<CanonicalInit>
  play(s, cmd): Promise<PlayResult>
  catalog?(): Promise<CatalogGame[]>
  mapError(e): CanonicalError
}

5. Canonical protocol

What "canonical protocol" means

Your own single request/response format that your lobby and games use, no matter which provider is behind. Like a travel plug adapter: your devices (games) have one plug; each country's socket (provider) gets its own adapter (connector). "Canonical" = the one official version you decided on. You design it, you own it.

Without it — every game must understand every provider

// Provider A
{ "nextStep": "freespin",
  "balance": { "amount": "102.50" } }

// Provider B (example)
{ "state": "FS", "balanceCents": 10250 }

With it — the game sees only your format

{ "next": { "action": "freespin" },
  "balance": "102.50" }

// connector A and connector B both
// translate into exactly this shape

Design the canonical protocol as a superset of the current Game API (it is your richest provider and already proven), then add three ideas that make it provider-neutral: one play command, an event list for presentation, and capabilities.

Init POST /v1/sessions

{
  session: { token, expiresAt, demo },
  game: {
    id, provider, title,
    layout: { reels:[3,3,3,3,3], winType:"lines"|"ways"|"cluster" },
    symbols: [{ id:"sym5", art:"gem_red", wild, scatter }],
    paylines?, paytable
  },
  money: { balance:"103.00", currency:"USD", decimals:2 },
  bets: { values:["0.10","0.25"…], default:"0.10" },
  capabilities: {
    buyFeature:{ priceMultiplier:100 }, turbo:false,
    autoplay:{ max:100 }, minSpinMs:2500, realityCheckMin:60
  },
  resume: PlayResult | null,   // last round to restore
  promos: { tournaments:[…], popups:[…] },
  i18n: { locale, bundles:[…] }
}

Play POST /v1/play

// request
{ requestId:"uuid", action:"spin",
  bet:"0.10", params:{ lines:10 } }
// action: spin | freespin | buy | respin |
// cascade | pickBonus | exitBonus | jackpot | pickCell

// response
{
  round: { id, status:"open"|"closed" },
  events: [
    { type:"reelsStop", reels:[…] },
    { type:"win", kind:"line", line:2, symbol:"sym3", amount:"0.50" },
    { type:"featureTriggered", feature:"freespins", count:10 },
    { type:"bigWin", tier:2 }
  ],
  totals: { stepWin:"0.50", roundWin:"0.50" },
  balance: "102.50",
  next: { action:"freespin", auto:true, options?:[…] },
  feature: { freespins:{ left:10, total:10 } },
  ext: { /* provider/game-specific, optional */ }
}

Why an event list

Snapshots force the client to diff states and know each provider's quirks. Ordered events (reelsStop → cascade → win → featureTriggered) let one renderer play any provider's round by mapping events to animations.

Why one /play

Different providers split actions across different endpoints. A single command with action keeps the client's next loop identical everywhere; connectors route to the real endpoint.

Why capabilities

Features and jurisdiction rules (e.g. UK: 2.5 s minimum spin, no autoplay or turbo) are decided once on the server. The client just obeys flags — no per-operator builds.

Escape hatch: ext

Avoids a lowest-common-denominator protocol. Game-specific data (Dark Portal modes, TapTap hash) travels in ext; only that game's feature module reads it.

7. Play flow with idempotency

Money moves on every play, so a retry after a network drop must not place a second bet. The client generates a requestId per action; the gateway stores the result for a short window.

8. Making the game client truly generic

A connector can translate the API, but the art still has to match the outcome. "Same game on another provider" only works if that provider runs the same (licensed / white-label) math, or the client is a data-driven engine configured by init.

Data-driven layout

Reel count and heights, win type (lines / ways / cluster), paylines and paytable all come from init.game. No per-provider builds.

Symbol registry

symbols[].art points to a sprite or Spine skin. The gateway holds a mapping table per provider × game (provider symbol ID → our art key).

Feature modules

Freespins, cascade, hold & win, pick bonus, wheel, jackpot field, mode switch. Each is a plug-in that listens to its events and reads its ext data.

Event player

The renderer walks events[] in order and maps each type to an animation. Unknown event types are skipped and logged — a new provider can't crash the client.

9. Lobby aggregation

The lobby reads one catalog from the gateway, which merges all providers' game lists into a single format.

Unified catalog item

{
  id: "prov-a:gameone",
  provider: "prov-a",
  title, thumbnails, tags,
  rtp: "95.50", volatility: "high",
  features: ["freespins","buy"],
  clientId: "gameone",   // which of OUR client builds to load
  jurisdictions: ["MT","SE"]
}

One kind of game

  • Every game uses our client and goes through our gateway; providers only supply the math.
  • Launch always returns our game URL with a gateway token.
  • No provider-built clients or provider URLs in the lobby.

Lobby features this unlocks

  • Cross-provider search, filters by feature, volatility, RTP
  • Recently played and favourites across providers
  • Cross-provider tournaments (gateway sees every round)
  • Per-operator catalog rules and geo filtering in one place

Who owns what

PartOwner
Game client (graphics, animations, HUD)Us — React + PixiJS, URL on our domain games.yoursite.com/<clientId>
Lobby, catalog, launchUs — via the gateway
Every spin / play actionUs — client → gateway → connector
Math, RNG, spin outcomesProvider
Money (debit / credit)Provider ↔ operator wallet

Result: full control over UI, tournaments and analytics for every game, at the cost of building a client (or reusing one by clientId) for each game before it can be listed.

What must be true for "same client, two providers"

Symbols map to your art

Every provider symbol has an entry in that connector's symbol table. Art is chosen by clientId + mapping, never by the provider.

Same game layout

Same reels (5×3) and same kind of features. If B's version is 6×4 with different features, it is a different game with the same name — it needs its own client build (a separate clientId).

Certification

Check whether your Fruit Storm client may run on Provider B's math in your markets.

11. Roadmap

Each phase ships on its own; no big-bang rewrite.

PHASE 0

Protocol + transport port

Define packages/protocol. Client codes against GameTransport. Ship a DirectTransport that converts the current Game API in the browser, plus MockTransport. No new servers.

PHASE 1

Gateway with Connector A

Stand up the gateway, move the Game API mapping server-side, add Redis session map and requestId idempotency. Switch clients to GatewayTransport. Runs on the free dev stack.

PHASE 2

Second provider + catalog

Add Connector B, unified catalog, symbol mapping tables so existing clients (e.g. Fruit Storm) run on Provider B.

PHASE 3

Hardening

Capabilities per jurisdiction, circuit breakers, audit replay tooling, cross-provider tournaments, WS push.

PHASE 4

Paid staging + prod

Move to Kubernetes in the providers' region with managed Redis HA and Postgres. Deploy with Argo CD from Git: one Application per environment, auto-sync for staging, manual sync for prod.
